Adaptive Insights — Persistent User Preferences

A 2026 IBM watsonx Hackathon project. I built the layer that makes the AI remember you — telling a preference apart from a question, storing it per user, and holding the interface steady enough to feel like yours while leaving room for it to still surprise you.

2026 IBM watsonx Hackathon — Personalization & Agent Memory

Teaching an Adaptive UI to Remember You

An AI that picks a fresh layout for every answer is impressive once and exhausting by the fourth question. Adaptive Insights lets a local model plan how each result is rendered; my contribution was the counterweight — persistent user preferences. Say “use dark mode, a purple palette, and bar charts by default” and the system recognizes it as an instruction rather than a query, writes it to a per-user store, and applies it to every session that follows. The hard part was never the file I/O. It was deciding who wins when a stored preference, a phrase in the current prompt, and the model’s own opinion all want a different chart — and then deciding how much freedom to leave the model once the user’s choices are locked.

My Contribution

Preference persistence — 2026 IBM watsonx Hackathon

I owned the personalization layer end to end: the LLM intent classifier that separates UPDATE_PREFERENCE and VIEW_PREFERENCES from QUERY_DATA, the per-user preference store behind it, and the precedence rule that resolves conflicts between a stored default, a phrase in the live prompt, and the render planner’s own choice.

Four settings persist across sessions — theme, palette, chart type and number format — and they reach both ends of the stack: injected into the planner’s prompt as the user’s standing defaults, and read directly by React when it paints colors and formats numbers.

The intent classifier runs at temperature 0 against a constrained JSON contract, returning an intent plus only the preference keys the user actually named — explicitly instructed not to invent values. It normalizes the vocabulary people really use: grey to gray, violet and lavender to purple, navy and cyan to blue, colorful to rainbow. If classification fails or the model is unreachable, the request degrades to QUERY_DATA and the user still gets an answer.

The store is keyed by username, merges partial updates over existing values rather than replacing the record, and falls back to documented defaults for anyone with no history — so a first-time user and a returning one take the same code path.

The UX position underneath all of it: an adaptive interface has to be predictable where the user has committed, and free everywhere else. Anything a person explicitly chose — theme, palette, chart type, number format — is treated as a promise and reproduced exactly. The details they never mentioned are where the interface is allowed to move: an accent, a card treatment, a legend position, a donut instead of a flat pie. Same shape you asked for, small delight you didn’t — and because the variation is drawn to differ from the one you saw last, the surface stays alive across a session instead of settling into a template.

The Challenge

In an interface where an LLM chooses the layout, personalization and adaptivity are in direct conflict. Let the model decide freely and the user’s saved defaults evaporate; hard-code the defaults and the adaptive planner becomes decoration. Worse, both failure modes look like bugs to the user — and neither is reliably reproducible when a 3B model is making the call.

My Approach

I made the arbitration explicit instead of emergent, as a three-tier precedence: what you asked for in this prompt beats what you saved, what you saved beats what the model preferred, and any choice that doesn’t fit the returned data shape loses to a deterministic fallback. Each outcome is stamped with a status — ollama+prompt, ollama+preference, fallback — so why a given view appeared is a fact in the response, not a guess.

Project Context

Adaptive Insights is the team’s hackathon entry: an analytics interface that decides how to answer, not just what. A prompt enters, a local Llama 3.2 model returns a render plan, and React draws whichever view fits the result — a spotlight for a single account, cards for a handful, a table for many, or a bar, pie, line, area, treemap or leaderboard for an aggregate. Three Docker services carry it: a Node.js broker that routes and validates, a Python service exposing MCP-style data tools, and Qdrant holding retrieval memory for report documentation. Everything, the reasoning model included, runs locally.

The architecture is described with a brain metaphor — the broker as thalamic routing, Qdrant as hippocampal memory, Ollama as cerebral reasoning, validation as cerebellar coordination, and a deterministic brainstem fallback that keeps the UI answering when the model is offline. Preference persistence is the long-term memory in that picture: the part that carries something forward from one session into the next.

What I Built

The path a preference travels: recognized in a sentence, written to a store, merged into the next session, defended against everything downstream that might overwrite it — and bounded, so the interface can still surprise you where you never expressed a preference.

Telling an Instruction From a Question

An LLM classifier routes every prompt to QUERY_DATA, UPDATE_PREFERENCE, or VIEW_PREFERENCES, so “use pie charts by default” is stored while “show revenue by region” is answered, and “show my settings” returns the saved record instead of searching for data. Few-shot examples pin the boundary cases — the ones where a preference and a query use nearly the same words.

A Per-User Store That Merges, Not Replaces

Preferences are namespaced by username and updated key by key, so setting a palette never silently clears a saved theme. Users with no history resolve to documented defaults, and a missing or unreadable store degrades to an empty object rather than throwing — the personalization layer can fail without taking the request with it.

Three-Tier Precedence, Stamped in the Response

An explicit request in the current prompt outranks a stored default, which outranks the model’s own plan, which loses to a deterministic fallback if it doesn’t fit the data. A stored chart type is applied only when the returned shape can carry it — a saved pie preference never turns a single record into a pie — and the response reports which rule fired.

Normalizing the Words People Actually Use

Colors arrive as synonyms, so both paths normalize them: grey to gray, crimson to red, lavender and violet to purple, magenta and rose to pink, colorful to rainbow. The regex extractor is ordered most-specific first so high contrast isn’t swallowed by a looser match, with guards against near-misses like “not pie”.

Inline Preferences, Captured in Passing

A preference mentioned mid-question — “show revenue by region in a dark theme” — is extracted from the prompt, merged over the stored record for this answer, and written back, so a user can drift into their preferred setup without ever visiting a settings screen or issuing an explicit command.

Preferences Reaching Both Ends of the Stack

The stored record is injected into the render planner’s prompt as the user’s standing defaults, and read again in React, where the palette drives Recharts series colors, the theme switches the shell, and the number format selects how revenue prints — compact, full, percentage, or currency — from one saved value.

Familiar, Not Identical

Alongside the preferences I persisted a variation history — the accent, card style, chart variant, legend position and decimal precision last shown — and the next variation is drawn to differ from it. The user’s stated choices are reproduced exactly; the unstated details are free to shift, so each answer feels attended-to rather than templated. The surprise is deliberately bounded: it never reaches a setting the user has committed to.
