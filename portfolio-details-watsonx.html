Adaptive Insights: Persistent User Preferences for an Adaptive UI

When a local LLM picks a fresh layout for every answer, the interface forgets what the user asked for, and a returning visitor has to restate the same settings each session. For our 2026 IBM watsonx Hackathon project, I built the preference layer that fixes this: an LLM classifier tells a preference apart from a question, saves it per user, and applies it in every later session, while details the user never specified stay free to vary.

Project Overview

Preference persistence — 2026 IBM watsonx Hackathon

I owned the personalization layer end to end: the LLM intent classifier that separates UPDATE_PREFERENCE and VIEW_PREFERENCES from QUERY_DATA, the per-user store behind it, and the precedence rule that resolves conflicts between a saved default, the live prompt, and the render planner’s own choice.

Four settings persist across sessions: theme, palette, chart type and number format. They reach both ends of the stack, added to the planner’s prompt as the user’s standing defaults, and read by React when it picks colors and formats numbers.

What I Built

Adaptive Insights is our team’s hackathon entry: an analytics interface where a local Llama 3.2 model returns a render plan for each prompt and React draws the view that fits, backed by a Node.js broker, a Python service with MCP-style data tools, and Qdrant for retrieval memory, all running locally under Docker Compose. My part was persistent user preferences. Every prompt first goes through an LLM intent classifier, run at temperature 0 against a fixed JSON contract with few-shot examples, which routes it to QUERY_DATA, UPDATE_PREFERENCE or VIEW_PREFERENCES and returns only the preference keys the user named, with color synonyms normalized (grey to gray, violet to purple, colorful to rainbow). Preferences land in a store keyed by username that merges updates key by key, so setting a palette never clears a saved theme. The saved record is added to the render planner’s prompt as standing defaults and read again in React, where the palette sets Recharts series colors, the theme switches the shell, and the number format decides how revenue prints.

Design Decisions

I wrote the precedence rule down instead of letting it emerge: a request in the current prompt beats a saved default, a saved default beats the model’s plan, and anything that doesn’t fit the returned data falls back to a fixed view. Each response is stamped with the rule that fired (ollama+prompt, ollama+preference, fallback), so why a view appeared is a fact rather than a guess. I also treated the four saved settings as promises reproduced exactly, and kept a variation history so unstated details like accent, card style and legend position shift between answers, which keeps the interface fresh without touching anything the user chose. Finally, the layer fails soft: if the classifier or model is unreachable the request falls back to QUERY_DATA, and a missing store returns an empty object, so the user always gets an answer.

The Result

Theme, palette, chart type and number format now persist across sessions. A user who asks for dark mode, a purple palette and bar charts in one session can come back, ask “show revenue by region”, and get a purple bar chart with the applied preference reported in the response, without ever opening a settings screen.

Key Features

Intent classification that separates saving a preference, viewing saved settings and asking a data question; a per-user store that merges partial updates and gives first-time users documented defaults; three-tier precedence with the winning rule stamped in each response; color synonym normalization backed by a regex extractor ordered most-specific first; inline preferences pulled from a question, applied to that answer, and saved; preferences applied in both the render planner and React; and a variation history that keeps unstated details changing from one answer to the next.
