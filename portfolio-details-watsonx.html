Adaptive Insights — Persistent User Preferences

A 2026 IBM watsonx Hackathon project. I built the layer that makes the AI remember you: it tells a preference apart from a question, stores it per user, and keeps the interface steady where you have chosen — free to vary everywhere else.

2026 IBM watsonx Hackathon — Personalization & Agent Memory

Teaching an Adaptive UI to Remember You

An AI that picks a fresh layout for every answer is impressive once and tiring by the fourth question. Adaptive Insights lets a local model plan how each result is drawn; I built the counterweight — persistent user preferences. Say “use dark mode, a purple palette, and bar charts by default” and the system reads it as an instruction rather than a question, saves it per user, and applies it in every session after. The hard part was not the file I/O. It was deciding who wins when a saved preference, the current prompt, and the model each want a different chart — and how much freedom to leave the model once the user’s choices are locked.

My Contribution

Preference persistence — 2026 IBM watsonx Hackathon

I owned the personalization layer end to end: the LLM intent classifier that separates UPDATE_PREFERENCE and VIEW_PREFERENCES from QUERY_DATA, the per-user store behind it, and the precedence rule that resolves conflicts between a saved default, the live prompt, and the render planner’s own choice.

Four settings persist across sessions — theme, palette, chart type and number format — and they reach both ends of the stack: added to the planner’s prompt as the user’s standing defaults, and read by React when it picks colors and formats numbers.

The classifier runs at temperature 0 against a fixed JSON contract, returning an intent plus only the preference keys the user actually named — it is told not to invent values. It also normalizes the words people really use: grey to gray, violet and lavender to purple, navy and cyan to blue, colorful to rainbow. If it fails or the model is unreachable, the request falls back to QUERY_DATA and the user still gets an answer.

The store is keyed by username and merges partial updates instead of replacing the record. Anyone with no history gets documented defaults, so a first-time user and a returning one take the same code path.

The idea underneath it: an adaptive interface should be predictable where the user has chosen, and free everywhere else. Theme, palette, chart type, and number format are treated as promises and reproduced exactly. The details nobody mentioned — an accent, a card style, a legend position, a donut instead of a flat pie — are where the interface can move. Each variation is drawn to differ from the last one, so the surface stays alive across a session without ever changing something the user asked for.

The Challenge

When an LLM chooses the layout, personalization and adaptivity pull against each other. Let the model decide freely and saved defaults disappear; hard-code the defaults and the planner becomes decoration. Both look like bugs to the user, and neither reproduces reliably when a 3B model is making the call.

My Approach

I wrote the rule down instead of letting it emerge. Three tiers: what you ask for in this prompt beats what you saved, what you saved beats what the model preferred, and any choice that doesn’t fit the returned data loses to a fixed fallback. Each response carries the rule that fired — ollama+prompt, ollama+preference, fallback — so why a view appeared is a fact, not a guess.

Project Context

Adaptive Insights is our team’s hackathon entry: an analytics interface that decides how to answer, not just what. A prompt comes in, a local Llama 3.2 model returns a render plan, and React draws whichever view fits — a spotlight for a single account, cards for a handful, a table for many, or a bar, pie, line, area, treemap or leaderboard for an aggregate. Three Docker services carry it: a Node.js broker that routes and validates, a Python service exposing MCP-style data tools, and Qdrant holding retrieval memory. Everything runs locally, including the model.

The team described the architecture with a brain metaphor — the broker as routing, Qdrant as memory, Ollama as reasoning, validation as coordination, and a fixed fallback that keeps the UI answering when the model is offline. Preference persistence is the long-term memory: the part that carries something from one session into the next.

What I Built

The path a preference travels: recognized in a sentence, saved, merged into the next session, and protected from anything downstream that might overwrite it.

Telling an Instruction From a Question

An LLM classifier routes every prompt to QUERY_DATA, UPDATE_PREFERENCE, or VIEW_PREFERENCES. “Use pie charts by default” is saved, “show revenue by region” is answered, and “show my settings” returns the saved record instead of searching for data. Few-shot examples pin down the cases where a preference and a question use nearly the same words.

A Per-User Store That Merges, Not Replaces

Preferences are namespaced by username and updated key by key, so setting a palette never quietly clears a saved theme. Users with no history get documented defaults, and a missing or unreadable store returns an empty object instead of throwing — the personalization layer can fail without taking the request down with it.

Three-Tier Precedence, Stamped in the Response

A request in the current prompt outranks a saved default, which outranks the model’s own plan, which loses to a fixed fallback if it doesn’t fit the data. A saved chart type applies only when the data can carry it — a saved pie preference never turns a single record into a pie — and the response reports which rule fired.

Normalizing the Words People Actually Use

Colors arrive as synonyms, so both paths normalize them: grey to gray, crimson to red, lavender and violet to purple, magenta and rose to pink, colorful to rainbow. The regex extractor is ordered most-specific first so high contrast isn’t caught by a looser match, and guards against near-misses like “not pie”.

Inline Preferences, Captured in Passing

A preference mentioned mid-question — “show revenue by region in a dark theme” — is pulled from the prompt, applied to this answer, and saved. Users can settle into their preferred setup without ever opening a settings screen.

Preferences Reaching Both Ends of the Stack

The saved record goes into the render planner’s prompt as the user’s standing defaults, and is read again in React: the palette sets Recharts series colors, the theme switches the shell, and one saved value decides how revenue prints — compact, full, percentage, or currency.

Familiar, Not Identical

Alongside the preferences I saved a variation history — the accent, card style, chart variant, legend position and decimal precision last shown — and the next variation is drawn to differ from it. Stated choices are reproduced exactly; unstated details are free to shift, so each answer feels considered rather than templated. The variation never touches a setting the user has chosen.
