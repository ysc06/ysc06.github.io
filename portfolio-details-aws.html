AWS Elastic Infrastructure

Cloud Infrastructure Project

Elastic Web Infrastructure on AWS

A single server is a single point of failure and a fixed ceiling on throughput. This project replaces it with infrastructure that has neither: an Application Load Balancer spreads HTTP requests across healthy Flask instances in two availability zones, and an Auto Scaling group watches average CPU and starts or stops instances on its own — each new machine configuring itself from a launch template and joining the load balancer with nobody touching a console.

Project Overview

What was demonstrated

Scale-out: under simulated CPU load, the Auto Scaling group started new instances against a 50% average CPU target. Each one passed its health check and began serving traffic on its own.

Scale-in: once demand fell away, the group shut the extra instances down again — capacity following demand in both directions, not just upward.

A hands-on AWS project: a Python Flask REST service on Amazon EC2, behind an Application Load Balancer, under an Auto Scaling group sized min 0 / desired 1 / max 3 across two availability zones. The goal was to work through the whole chain — networking, health checks, bootstrapping, and elasticity — rather than any one piece on its own.

The Challenge

Elasticity only works if a machine that did not exist a minute ago can configure itself, pass a health check, and start taking real traffic with no manual step in between. That means the security groups, the target group, the health-check path, and the startup script all have to be right at once. Get any one wrong and instances launch but quietly never receive a request.

My Approach

An EC2 launch template with a startup script that installs dependencies, pulls the application code, and starts the service on boot; security-group rules scoped so the load balancer — and only the load balancer — can reach the application port; and a target-tracking policy driven by CloudWatch average CPU. Then I tested it the only way that counts: generating CPU load and watching instances appear, register, and later go away.

Key Features

Routing, health checks, bootstrapping, and the policy that decides how many machines exist at all.

Load-Balanced Flask Services on EC2

Python Flask REST services on Amazon EC2, with an Application Load Balancer and target group spreading HTTP requests across every instance currently reporting healthy.

Security Groups & Health Checks

The application port is open to the load balancer rather than the internet, and a health endpoint tells the target group when an instance is genuinely ready to serve.

Self-Bootstrapping Launch Template

An EC2 launch template carrying a startup script that installs dependencies, fetches the application code, and launches the service — so a brand-new instance serves traffic with no manual setup.

CPU-Driven Target Tracking

An Auto Scaling group across two availability zones adds and removes capacity to hold average CPU near its target, rather than reacting to hand-set thresholds.

Verified Scale-Out and Scale-In

Scale-out was tested under simulated CPU load, confirming that new instances joined the load balancer on their own. Scale-in was checked after demand dropped, so idle capacity is released rather than left running and billed.
